# FPGA ONFI Controller — рабочий контекст варианта 3

Этот каталог собирает редактируемую спецификацию, результат её сборки, шаблон оформления и исходные материалы, использованные в обсуждении проекта. Исходники находятся в `specification/`, эталонный шаблон — в `template/`, документы и снимки задания — в `references/`.

## Текущее состояние

- Проект: командный FPGA ONFI Controller, вариант 3 — конечный автомат протокола и логика управления.
- Спецификация: `specification/specification.typ`, собранный PDF: `specification/specification.pdf`.
- Для титульника и оформления рядом находится копия `layout.typ`.
- Шаблон отчёта с инструкциями: `template/report.typ`, `template/layout.typ`, `template/report.pdf`.
- `references/` содержит требования преподавателя, варианты 2–5, прежний пример отчёта и локальные копии Avalon/ONFI материалов.

Пересобрать спецификацию из каталога `task2/specification`:

```sh
typst compile specification.typ specification.pdf
```

## Зафиксированные рабочие предположения

- Avalon-ST: шина данных 64 бита, передача происходит на фронте `clk`, если `valid` и `ready` одновременно равны 1. Границы пакета передаются отдельными сигналами SOP/EOP, `empty` отмечает неиспользуемые младшие байты последнего слова.
- ONFI: базовый профиль ONFI 2.0, асинхронный режим, один LUN; максимум тела операции первой модели — 512 байтов.
- Вариант 3 принимает и разбирает пакет, планирует команды/адрес/данные PHY, принимает результат и формирует ответ.
- Внутренние каналы `cmd`, `w`, `r`, `done` и record адреса предложены как проектный контракт для согласования с разработчиком PHY (вариант 5).
- Очереди должны позволять приём пакета, пока PHY исполняет предыдущий запрос, и выдачу ответа параллельно исполнению следующего запроса. При заполнении очередь использует обратное давление через `ready`.
- В проекте предусмотрены девять обязательных ONFI-команд M и две операции управления режимом через Get/Set Features. Пользовательские OPCODE — это формат команды контроллера, они не совпадают с ONFI opcode.

## Открытые вопросы

1. Преподаватель должен подтвердить требуемую степень параллельности, трактовку байтовой MASK, лимит 512 байтов и достаточно ли одного LUN/асинхронного ONFI 2.0 для защиты.
2. Варианты Avalon-ST Master/Slave должны подтвердить OPCODE `0x08–0x0B`, формат тела смены колонки/режима и правила MASK.
3. Команда буферизации должна подтвердить раздельные классы очередей чтения/записи, резервирование полного пакета и результатного буфера, порядок ответов и сброс.
4. PHY должен подтвердить набор каналов и фаз, формат адресного record, timing modes, поддержку смены колонки при программировании, R/B# handshaking и восстановление после тайм-аута.
5. Выбранная NAND определит геометрию, число адресных циклов, задержки и ограничения маскированной записи.

Текущая Typst-спецификация — архитектурное предложение, а не утверждённый всеми участниками интерфейс и не результат реализации/верификации.

## Версии источников

- Для реализации Avalon-ST используйте редакцию Avalon Interface Specifications от 24 января 2022 года, глава 5. Скан редакции Altera 1.2 за апрель 2009 года оставлен для первичного знакомства с понятиями `valid/ready`, SOP/EOP и `empty`.
- Для задания PHY используйте ONFI 2.0 от 27 февраля 2008 года. Конкретная NAND дополнительно потребует сверки своего datasheet.
- Локальные документы сохранены в `references/`. Первичные файлы вариантов 3 и 4 — те PDF, на которых основывался текущий разбор; они не заменяют подтверждённую спецификацию преподавателя.
